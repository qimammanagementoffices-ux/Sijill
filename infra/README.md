# Infra

Render topology (architecture review item #11): separate frontend/API
services, managed Postgres, object storage hosted externally.

The actual Render Blueprint lives at `../render.yaml` (must stay at repo
root for Render to auto-detect it). It provisions:

- `sijill-postgres` — managed Postgres (free plan)
- `sijill-api` — Spring Boot backend, built from `../backend/Dockerfile`
  (multi-stage Gradle build, no local wrapper needed)
- `sijill-frontend` — Next.js frontend, Render's native Node runtime

## Deploying

1. Push this repo to GitHub.
2. In the Render dashboard: **New > Blueprint**, point it at the repo.
   Render reads `render.yaml` and creates all three resources.
3. Set the `sync: false` env vars manually in the Render dashboard before
   first deploy (or after — the API just won't have real object storage
   until they're set):
   - `OBJECT_STORAGE_ENDPOINT`, `OBJECT_STORAGE_BUCKET`,
     `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY` — point these
     at an S3-compatible bucket (Render has no built-in object storage;
     Cloudflare R2 or AWS S3 both work). Not required for the app to boot
     in Phase 1 (no upload feature exists yet), but will be once file
     upload ships.
4. `JWT_SIGNING_SECRET` is auto-generated by the blueprint
   (`generateValue: true`) — don't need to set it.
5. Free-tier caveats: free Postgres expires after ~30 days unless
   upgraded; free web services spin down after 15 min idle (cold start on
   next request). Fine for early testing, not for real users.

Local dev still uses `docker-compose.yml` at the repo root, not anything
in this folder.
